=== What Stage 2 Lite changes ===

The REDIRECT approach (current):
  App TCP → nat OUTPUT → REDIRECT --to-ports 10810 → daemon reads SO_ORIGINAL_DST

The TPROXY approach (Stage 2 Lite):
  App TCP → mangle OUTPUT → TPROXY --on-port 10810 --tproxy-mark 0x1/0x1
  ip rule add fwmark 0x1/0x1 table 100
  ip route add local 0.0.0.0/0 dev lo table 100
  (same for v6: ip -6 rule/route)
  Daemon binds with IP_TRANSPARENT, reads LocalAddr() directly (no syscall)

=== Technical details for the TPROXY listener (Go) ===

The daemon needs IP_TRANSPARENT on the listening socket. In Go:

  import "golang.org/x/sys/unix" // or use syscall directly
  
  lc := net.ListenConfig{
    Control: func(network, address string, c syscall.RawConn) error {
      var opErr error
      c.Control(func(fd uintptr) {
        opErr = syscall.SetsockoptInt(int(fd), syscall.SOL_IP, syscall.IP_TRANSPARENT, 1)
        if opErr == nil {
          // For v6 support on dual-stack socket:
          opErr = syscall.SetsockoptInt(int(fd), syscall.SOL_IPV6, 75 /* IPV6_TRANSPARENT */, 1)
        }
      })
      return opErr
    },
  }
  listener, err := lc.Listen(ctx, "tcp", ":10810")

Then on accept:
  conn, _ := listener.Accept()
  originalDst := conn.LocalAddr() // This IS the real destination
  // conn.RemoteAddr() is the app's source
  // Forward to SSH tunnel targeting originalDst

=== HyperOS mangle table context (from diagnostic) ===

The phone's existing mangle OUTPUT chain has:
  1. qcom_NWMGR (empty)
  2. connmark_mangle_OUTPUT (CONNMARK save mask 0xfffff)
  3. qos_reset_OUTPUT (empty)

And POSTROUTING has:
  5. qcom_qos_reset_POSTROUTING: MARK and 0x0 (clears marks on rmnet_data+)

The routectrl_mangle_INPUT stamps: MARK xset 0x30069/0x7fefffff on rmnet_data2

Our TPROXY rules go at OUTPUT position 1 (before all of the above).
Our fwmark 0x1/0x1 uses bit 0 which HyperOS doesn't touch (their masks 
use 0x7fefffff and 0xfffff — both have bit 0 as part of the mask but the 
actual values they SET don't use bit 0: 0x30069 has bit 0 = 1 only in the 
LSB which is the netId... wait, 0x30069 = 0b11_0000_0000_0110_1001, bit 0 
IS set. So we need a DIFFERENT bit.)

CORRECTION: Use bit 23 (0x800000) instead. HyperOS's masks are 0x7fefffff 
(bit 23 = 0 in their mask) and 0xfffff (only low 20 bits). So bit 23 is 
completely untouched by HyperOS. Use fwmark 0x800000/0x800000 for TPROXY.

Actually safer: use a high bit. Let's use 0x20000000 (bit 29). 
HyperOS mask 0x7fefffff = bits 0-20 + 22-30, so bit 29 IS in their mask.

Safest approach: Use 0x1/0x1 BUT insert our TPROXY rule at OUTPUT pos 1 
(before HyperOS's connmark_mangle_OUTPUT which only does CONNMARK save). 
The qcom_qos_reset_POSTROUTING does "MARK and 0x0" which CLEARS all marks, 
but that's POSTROUTING — by then the packet has already been delivered to 
our TPROXY socket via the fwmark policy route in OUTPUT. The ip rule/route 
lookup happens at OUTPUT time, not POSTROUTING. So 0x1/0x1 is fine.

FINAL ANSWER ON FWMARK: Use 0x1/0x1. It works because:
1. Our rule is -I OUTPUT 1 (runs first)
2. TPROXY stamps 0x1/0x1 on the packet
3. Policy routing (ip rule fwmark 0x1/0x1 table 100) matches in OUTPUT
4. Packet gets delivered to our TPROXY socket on lo
5. HyperOS's later POSTROUTING rules that clear marks don't matter — 
   delivery already happened
