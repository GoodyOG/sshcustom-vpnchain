Hello! I've now read the actual daemon sources (main.go, client.go, config.go) and all three lifecycle scripts (ssh.service, ssh.tool, ssh.iptables), so my analysis below is grounded in the real code rather than the handoff. Here's the full breakdown of those logs.

Line-by-line log analysis
Phase 1 — Boot (12:55), idle daemon
boot service started → boot ready (waited 15s) → starting daemon in idle mode
autostart disabled — daemon idle at 127.0.0.1:9190
service: daemon started pid=7821 flags=... --idle
[http] listening on 127.0.0.1:9190
This is service.sh calling ssh.service start-idle because the autostart marker isn't set. The daemon launches with --idle, which (per main.go) skips tunnelLoop entirely — it only brings up the two control APIs. So at boot, nothing tries to connect. That's correct/expected behavior.

About 9190: that's the daemon's hardcoded local HTTP control API — httpSrv.Addr = "127.0.0.1:9190" in main.go. It's bound to loopback only and is completely separate from your proxy ports (SOCKS 1081, redir 9799, tproxy 9899). The companion app talks to the daemon over this port (plus the unix socket sshcustomd.sock). Seeing 9190 is normal — not a misconfiguration.

Phase 2 — You hit Start (13:05), active daemon
service starting...
service: daemon started pid=22094 flags=-c ... -w ...   (no --idle)
service: API ready
The app sent control start → handleControl → ssh.service start → start_daemon. It detected the old daemon was in --idle mode, killed pid 7821, and relaunched as pid 22094 without --idle, so now tunnelLoop is running.

ssh.tool[192]: can't create /dev/blkio/sshcustom/blkio.weight: Permission denied
Cosmetic. start_service calls ssh.tool blkio. Your kernel exposes a blkio cgroup mount at /dev/blkio, but it won't let a new sshcustom sub-cgroup be created/written (SELinux or restricted v1 controller). The script tries to suppress this with 2>/dev/null, but it leaks anyway because of a shell quirk: in cmd > file 2>/dev/null, the > file redirection is set up before 2>/dev/null takes effect, so when opening the file fails the shell prints the error to the still-original stderr. Harmless — blkio is a "nice-to-have" I/O priority tweak — but it's noise I can silence in this release if you want (reorder the redirection / pre-check writability).

cap: tproxy4=true tproxy6=true conntrack=true connmark=true ipset=false ip6_nat=false
iptables: mode=redirect dns=redirect quic=disable ipv6=false
ssh.iptables enable ran. Your kernel supports TPROXY + conntrack + connmark; no ipset, no IPv6 NAT. Current mode is redirect, and dns=redirect is the current default we're about to flip to disable.

A CONNECT payload, a WebSocket upgrade, a GET/POST host-injection, a split/multi-request payload, or even a raw non-HTTP prefix should all work. The daemon shouldn't care what the payload is.

What "generic" actually requires (how the injector apps do it)
In HTTP Injector / Custom, the payload is just raw bytes with tokens, sent to the remote. The only thing the client does afterward is: drain whatever HTTP acknowledgement the server/CDN sends, then treat the socket as a raw tunnel and start SSH. The current daemon skips that drain entirely, so SSH eats the HTTP reply and overflows. The generic fix has three parts:

Drain any HTTP response, regardless of status. After writing the payload, if the server replies with an HTTP/... block, consume the full status line + headers up to the blank \r \r . Don't validate the code — 101, 200, 302, whatever. Just log the status line for visibility and let the SSH handshake be the real success/failure test. This is exactly how injectors behave (they're lenient about the response).

Handle multiple responses and the no-response case. Some payloads produce two HTTP responses (a "front" request then the real tunnel request); some produce none (a pure raw prefix where the SSH banner comes straight back). So: keep consuming response blocks only while the incoming data starts with HTTP/; the moment it doesn't (e.g., it's SSH-2.0-…), stop and hand off to SSH. With a bounded read deadline so a silent server can't hang us — if nothing HTTP-looking arrives, we just proceed.

Don't lose the SSH banner (the tricky part). The upstream SSH server usually sends its SSH-2.0-… banner immediately after the upgrade, so it often arrives glued onto the tail of the HTTP response in the same TCP read. If I naively buffer the response I'd swallow those banner bytes. So I'll wrap the socket in a small prefix-buffer connection that replays any already-read tunnel bytes to the SSH layer first, then passes through to the raw socket. This guarantees zero byte loss for any payload shape.

Net effect: the payload field becomes a transparent pipe — you paste the same payload that works in HTTP Custom, and the daemon sends it, clears the server's acknowledgement, and starts SSH on the raw stream. No payload type is privileged.

Tokens (the other half of "any payload")
Send-side, your payload uses [crlf], which the daemon already substitutes (along with [host], [port], [cr], [lf]). Injector apps also support tokens like [ua], [host_port], [protocol], and DPI-evasion tokens like [split]/[delay] (which chunk the payload). I've reviewed the updated logs and the SSH client code. There's a lot here, and the logs reveal the single most important issue. Here's my extensive analysis — no code changed yet; I want your decisions on a few things before implementing.

The headline finding: your SSH connection is dropping every ~20 seconds
This is the root cause of almost everything you're feeling ("apps think I disconnect for a sec"). From your redirect log:

17:58:53 [tunnel] connected
17:59:14 [tunnel] SSH connection lost: EOF      ← 21 seconds later
17:59:14 [tunnel] tearing down → iptables disabling → all rules removed
17:59:17 [tunnel] connecting … 
17:59:18 [tunnel] connected → rules re-applied
The server (the bc.game WebSocket bridge → your SSH) is closing the connection with EOF after ~21s, then the daemon rebuilds it. During that ~4s rebuild, the iptables rules are removed and re-added — so every app's traffic blips. That's exactly the "offline for a sec" you see in both redirect and tproxy.

Why it drops at ~21s: two compounding causes:

SSH keepalive is too slow. It's set to 30s, but the WebSocket/bug-host path is being torn down at ~20s of idle — before our first keepalive fires. A ~10s keepalive would generate traffic early enough to keep the path alive.
The channel pool is hammering the server. On connect, the pool tries to pre-open 8 SSH channels to 127.0.0.1:7 (a discard port) on the server. That port refuses, so it retries a failed channel-open every 500ms forever. Many SSH/bridge servers drop a client that floods failed channel requests — this may be causing the 20s EOF, and it's why the pool is stuck (next item).
Fix plan: drop the SSH keepalive to ~10s, and remove the channel-pool warming entirely (it's broken and likely harmful). If the connection stays up, the blips disappear and WAN resolves.

"0/8 channels" — what it is and why it's stuck (your explicit ask)
The "channel pool" is a pre-warming optimization: the daemon tries to keep 8 SSH channels pre-opened so the first connection through the tunnel doesn't pay channel-setup latency. To warm them, it opens throwaway channels to 127.0.0.1:7 on the server side. Your server refuses port 7 (nothing listens there), so no channel is ever added → it's permanently stuck at 0/8, while it pointlessly retries twice a second. It does not affect real traffic (actual connections open their own channels on demand — that's why "active" works). It's misleading and, as above, possibly causing your disconnects. Recommendation: remove the channel pool feature (removes the "0/8" confusion and the server hammering). The "active" count is the genuinely useful number.

Home: WAN / Net Speed / Resources show nothing
In v2.0.7 these are all produced by the daemon. Since your "active connections" number updates, the app is reading fresh status — so the daemon's metrics loop is running. A few things are going on:

WAN is almost certainly a casualty of the flapping above: it's resolved through the tunnel on connect and cleared on every disconnect. With the link dropping every ~20s, the lookup never finishes before it's wiped. Fix the disconnects → WAN resolves.

Net Speed is daemon-computed in v2.0.7 (up_kbps/down_kbps), but only the v2.0.7 APK reads those fields.
