1. What I think is actually happening on your Poco F6 / HyperOS 3

Your current module (internal/iptables/iptables.go + net_clean.sh) does REDIRECT-only, TCP-only, IPv4-only, no DNS hijack, no fwmark integration. On a stock-AOSP custom ROM, that's mostly fine because the network stack is plain. On HyperOS 3 it's not, for these specific reasons — these are the prime suspects for "some stuff doesn't work or is slow":
#	Suspect	Why it bites HyperOS 3 specifically
A	UDP is never tunneled. Your chain does -p tcp -j REDIRECT --to-ports 10810. Anything UDP — QUIC (Chrome/YouTube/Meet/Maps), WebRTC, game voice, push — falls through to direct WAN.	HyperOS aggressively prefers QUIC. Carrier may rate-limit/black-hole UDP from a CGNAT user → looks like "slow loading" on YouTube/Chrome but TCP sites are fine.
B	No DNS hijack. Apps that ship their own resolver (Chrome DoH, Private DNS, Firebase, sing-box-ish apps) talk to 8.8.8.8:443 or DoT directly. SOCKS only sees the IP, not the name.	HyperOS 3 default Private DNS is on. So even your tunneled TCP carries a "wrong" IP because the lookup happened at a DNS server the tunnel didn't influence.
C	MIUI/HyperOS netd "mark coloring." Xiaomi's netd stamps every socket with an fwmark identifying the network it bound to. AndroidTProxyShell explicitly added a fix: --mark $MARK/$MARK (mask match) precisely because MIUI's coloring breaks plain --mark $MARK matching.	You don't use marks at all today, so on simple flows you're OK — but as soon as you stack vpnchain (which DOES use marks), the netd-set bits collide. This is exactly the kind of thing that makes "some apps work, some don't" on a per-app basis.
D	No IPv6 path. iptables.go calls iptables only, never ip6tables. HyperOS + most modern carriers hand out IPv6.	Apps with IPv6 connectivity (Google, Cloudflare-fronted, anything dual-stack) completely bypass your tunnel and go direct. If the carrier or your VPN blocks v6, the apps look broken; if it works, you're leaking your real v6 address.
E	vpnchain ordering risk. vpnchain.sh does iptables -t nat -I OUTPUT 1 -m owner --uid-owner 10000-99999 -j RETURN to bypass SSHCustom for app traffic going to tun0. But iptables.Apply() in Go also does -I OUTPUT 1 -p tcp -j SSHC_OUTPUT. Whichever runs last ends up at position 1. If SSHCustom restarts (watchdog/network resume) while vpnchain is up, the bypass moves to position 2, then SSHC_OUTPUT eats those packets first and the daemon's UID-0 RETURN doesn't help apps.	A daemon restart silently breaks vpnchain. Your symptom would be "works initially, breaks after a network change."
F	No conntrack flush on apply. Connections opened before tunnel-up keep their pre-NAT state in the kernel. Long-lived sockets (Telegram, FCM, push) sit on the old route until the app reconnects.	HyperOS's "always-on" services (GMS, MIUI services) hold sockets across radio events. Looks like "WhatsApp messages don't deliver until I toggle airplane mode."
G	No QUIC fallback rule. Combined with (A), no rule blocks UDP/443. Chrome will keep trying QUIC, time out, then fall back — and that timeout is the "slow loading."	The CHIZI script calls this out and adds BLOCK_QUIC.
H	HyperOS 3 NetworkPolicyManager / Battery saver. App standby buckets and "MIUI optimization" can move apps to restricted-networking, where iptables OUTPUT runs but the socket itself is delayed. Not your module's fault, but worth ruling out.	Per-app slowness with no rule mismatch in logs.
2. What CHIZI-0618/AndroidTProxyShell actually gives you (filtered, no China stuff)

After reading the entire tproxy.sh, here are the parts that are directly relevant to your problem, and the parts you can ignore.
Keep / steal

    TPROXY support (the headline). Uses iptables -t mangle -j TPROXY --on-port X --tproxy-mark M plus a policy-routing rule ip rule add fwmark M table T and ip route add local 0.0.0.0/0 dev lo table T. This is the right way to do TCP+UDP transparent proxying without rewriting destination addresses. Your daemon would need a TPROXY listener (the IP_TRANSPARENT socket option) to consume it.
    Auto-fallback to REDIRECT when kernel lacks TPROXY (PROXY_MODE=0). Saves your bacon on devices where the kernel was stripped.
    DNS hijack (DNS_HIJACK_ENABLE) with both REDIRECT and TPROXY variants — fixes (B) above.
    PERFORMANCE_MODE=1 — uses conntrack --ctstate NEW,RELATED + CONNMARK + --mark $mark/$mark, so that:
        Existing flows aren't reprocessed by the nat hook every packet (much less CPU).
        The mask match coexists with MIUI/HyperOS netd's mark coloring — fixes (C).
        Reply-direction packets are accepted by -m conntrack --ctdir REPLY -j ACCEPT early — preserves Android RPF strict mode.
    block_loopback_traffic — a filter rule rejecting core's own UID from talking to its own listener port. Belt-and-suspenders against tunnel-loop bugs in addition to your uid-owner 0 RETURN.
    BLOCK_QUIC — fixes (G). Single iptables rule: REJECT UDP/443 globally.
    Per-app whitelist/blacklist via find_packages_uid reading /data/system/packages.list. Cleaner than your current vpnchain "uid 10000-99999 blanket bypass."
    Interface-scoped chains — separate chains for mobile/wifi/hotspot/USB so you can proxy mobile data only, or hotspot only. Right now your module's hotspot mode is monolithic.
    IPv6 chain set (mirror of v4 in mangle/nat6). Fixes (D).
    Reply-direction -m conntrack --ctdir REPLY -j ACCEPT at the top of every chain. This is the single biggest thing missing from your design — without it, return packets from established connections re-enter your nat hook every time, causing CPU and occasional misroutes.

Skip (irrelevant for you)

    China IP bypass (BYPASS_CN_IP, cnip/cnip6 ipsets, GeoIP downloads). Useless outside CN.
    TZ=Asia/Shanghai. Cosmetic.
    The MAC blacklist/whitelist for hotspot — interesting but not your current scope.
    The "force disable IPv6 stack entirely" mode. Heavy hammer; you want IPv6 handled, not killed.
    All the pre_start_hook / post_stop_hook indirection. Your daemon is the orchestrator, you don't need shell hooks.

Verdict

Yes, this script is worth borrowing from. The architectural model — mangle-table TPROXY chains with a fwmark + lo-table route, plus reply-conntrack accept and mask-aware mark match — is exactly what's missing from your module. I would not import the script wholesale; I'd port the pattern into your Go iptables.go and add a TPROXY listener mode to the daemon, gated by a config flag so you can A/B against the current REDIRECT path. But that's tomorrow. Today is diagnosis.

      if (!d) return 'not checked';
      if (!d.ok) return d.error || 'lookup failed';
      const loc = [d.city, d.region, d.country].filter(Boolean).join(', ') || 'unknown location';
      const net = [d.isp, d.asn].filter(Boolean).join(' - ') || 'unknown network';
      return loc + ' / ' + net + (d.cached ? ' / cached' : '');
    }

    function renderStatus(data) {
      const s = data.runtime;
      const cfg = data.config || {};
      const connected = !!(s.connected && s.ssh_authenticated);
      const busy = !!(s.running && !connected);
      const standby = !!(s.running && s.state === 'PAUSED_NO_NETWORK');
      const tunnelActive = s.running;

      // Status dot — always pulses, color reflects tunnel state
      if (connected) {
        $('statusDot').className = 'status-dot connected';
        $('statusText').textContent = 'connected';
      } else if (standby) {
        $('statusDot').className = 'status-dot connecting';
        $('statusText').textContent = 'standby';
      } else if (busy) {
        $('statusDot').className = 'status-dot connecting';
        $('statusText').textContent = 'connecting';
      } else {
        $('statusDot').className = 'status-dot';
        $('statusText').textContent = 'disconnected';
      }

      // Hero card
      if (connected) {
        $('heroIcon').textContent = 'ON';
        $('heroTitle').textContent = 'Tunnel Connected';
        $('heroSubtitle').textContent = s.last_error || s.last_event || ('SSH pool healthy ' + (s.pool_healthy||0) + '/' + (s.pool_size||0));
      } else if (standby) {
        $('heroIcon').textContent = '||';
        $('heroTitle').textContent = 'Standby';
        $('heroSubtitle').textContent = 'Waiting for network connectivity to resume tunnel.';
      } else if (busy) {
        $('heroIcon').textContent = '...';
        $('heroTitle').textContent = s.state || 'Connecting';
        $('heroSubtitle').textContent = s.last_error || s.last_event || 'Establishing SSH tunnel...';
      } else {
        $('heroIcon').textContent = 'OFF';
        $('heroTitle').textContent = 'Disconnected';
        $('heroSubtitle').textContent = 'Tap Start Tunnel to connect.';
      }
      $('heroChips').innerHTML = '';

      // Buttons — contextual based on tunnel state
      updateButtons(tunnelActive);

      // Device IP
      $('deviceIp').textContent = s.source_ip || '--';
      const meta = [];
      if (s.interface) meta.push('via ' + s.interface);
      if (s.gateway) meta.push('gateway ' + s.gateway);
      $('deviceIpMeta').textContent = meta.length ? meta.join(' / ') : (s.network_online ? 'route detected' : 'no network route');

      // Tunnel Uptime — use tunnel_uptime_seconds
      $('runtimeValue').textContent = s.tunnel_uptime_seconds ? fmtUptime(s.tunnel_uptime_seconds) : '--';
      $('runtimeMeta').textContent = tunnelActive ? ([s.selected_mode, s.transport_chain].filter(Boolean).join(' / ') || 'Tunnel active') : 'No active session';

      $('perfValue').textContent = (s.cpu_percent || 0).toFixed(1) + '% CPU';
      $('perfMeta').textContent = 'RSS ' + fmtBytes(s.memory_rss_bytes) + ', system mem ' + (s.system_mem_used_percent || 0).toFixed(0) + '%';
      $('cpuValue').textContent = (s.cpu_percent || 0).toFixed(1) + '%';
      $('memoryValue').textContent = fmtBytes(s.memory_rss_bytes);
      $('memoryMeta').textContent = 'system memory ' + (s.system_mem_used_percent || 0).toFixed(0) + '% used';
      $('poolValue').textContent = (s.pool_healthy || 0) + '/' + (s.pool_size || 0);
      $('poolMeta').textContent = (s.pool_healthy === s.pool_size) ? 'all healthy' : 'reconnecting...';
      $('streamsValue').textContent = String(s.pool_streams || 0);
      $('streamsMeta').textContent = 'target ' + (s.pool_max_streams || '--') + ' streams per SSH';
      $('routeValue').textContent = s.interface || '--';
      $('routeMeta').textContent = s.gateway ? 'gateway ' + s.gateway : (s.source_ip || 'gateway unavailable');
      $('resolverValue').textContent = s.resolver_method ? 'android_shell_dns' : (s.dns_mode || '--');
      $('resolverMeta').textContent = (s.resolved_ips || []).join(', ') || 'no DNS activity yet';
      $('transparentMeta').textContent = s.transparent_running ? 'listening on ' + (s.transparent_addr || 'transparent port') : 'not running';
      $('socksMeta').textContent = s.socks_running ? 'listening on ' + (s.socks_addr || 'SOCKS port') : 'not running';
      renderNetworkConfig(cfg);
    }

    async function saveProfile(select, restart) {
      try {
        const mode = $('pfMode').value;
        const usesProxy = mode.includes('http_proxy');
        const usesTLS = mode.includes('tls');
        const req = {
          id: profileEditId,
          name: $('pfName').value.trim() || 'SSHCustom Profile',
          select,
          restart,
          ssh: {
            host: $('pfHost').value.trim(),
            port: parseInt($('pfPort').value, 10) || 22,
            username: $('pfUser').value.trim(),
            password: $('pfPass').value,
            auth_type: 'password'
            // fallback_ips removed in v2.0.0: hostnames resolve through the
            // daemon's smart resolver. If a profile previously had fallback_ips,
            // the daemon keeps them intact in profiles.json on save.
          },
          transport: {
            mode,
            http_proxy: usesProxy ? {
              host: $('pfProxyHost').value.trim() || $('pfHost').value.trim(),
              port: parseInt($('pfProxyPort').value, 10) || 80,
              connect_method: 'socket'
            } : undefined,
            tls: usesTLS ? {
              enabled: true,
              server_name: $('pfSni').value.trim() || $('pfHost').value.trim(),
              insecure_skip_verify: true,
              alpn: ['http/1.1']
            } : undefined,
            payload: {
              enabled: $('payloadSwitch').classList.contains('on'),
              template: $('pfPayload').value,
              send_timing: usesProxy ? 'after_proxy_socket_before_ssh' : 'before_ssh',
              read_response: true,
              allow_http_status: [101, 200, 204, 302]
            }
          }
        };
        await postV1('/profile/save', req, 12000);
        closeProfileEditor();
        if (restart) {
          toast('Profile saved. Restarting tunnel...');
          showRestarting();
          setTimeout(loadStatus, 3000);
        } else {
          toast('Profile saved.');
        }
        await loadProfiles();
      } catch (e) {
        toast('Profile save failed: ' + e.message, 'error');
      }
    }

    // --- REFRESH ENGINE ---
    // Primary: reliable polling loop (like the proven old version).
    // Enhancement: SSE for instant status updates when connected.
    // The polling loop ALWAYS runs — SSE just makes status updates faster.
    let tick = 0;
    let pollTimer = null;
    let sseSource = null;

    function refresh() {
      tick++;
      loadStatus();
      // Refresh page-specific content on slower cadences

Universal compatibility
Mechanism	Why it's ROM-agnostic
IPv6 lockdown	Uses ip6tables -t filter which every Android kernel since 4.4 has (CONFIG_IP6_NF_FILTER). Doesn't need IPv6 NAT (which many kernels lack).
QUIC block	Plain iptables -t filter rule. Works on literally any Android kernel ever shipped.
Conntrack flush	Tries three fallback methods — one of them will work on any kernel that has conntrack (all of them do).
Sysctl hardening	Writes to /proc/sys/net/ipv4/conf/*/route_localnet and rp_filter — standard Linux since 2.6, present on every Android build.
Where it helps most vs least
Scenario	Improvement
CGNAT carriers that whitelist hosts (your MTN case, Airtel zero-rated, Glo freebies, etc.)	Massive — every leaked packet = 8s timeout. Now zero leaks.
Normal carriers with full internet	Moderate — IPv6 bypass was invisible because v6 worked fine direct. But QUIC block still helps if you want ALL traffic through the tunnel (privacy). Conntrack flush ensures tunnel applies instantly.
Custom ROMs (LineageOS, PixelOS, etc.)	Works identically. These ROMs have cleaner netd code (no HyperOS mark coloring), so there are even fewer edge cases.
MIUI / HyperOS / ColorOS / OneUI	Works. The leak protection rules sit in the filter table, above any ROM-specific mangle-table QoS chains. They don't conflict.
Kernels without TPROXY	Works fine — we don't use TPROXY yet. Everything is filter-table REJECT + nat-table REDIRECT.
